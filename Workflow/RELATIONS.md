# Workflow - relations to the other projects

A hypothesis ledger, as in the other projects. Each entry is a claim, its status in the record's own terms (**stated**, **seen**, **open**), where the evidence is, and what is still open. A claim lives in the project that makes it; entries are added, updated or marked rejected, never removed. This project also writes here what it asks of the other projects; the asks are made there, under those projects' own plans, never from here.

---

## W-R1. The semantics is the authority, and only file 10
**Claim.** Every term the programme uses is file 10's, quoted at the sentence; where the programme builds an object the theory permits but does not contain, it says so. File 20 is set aside (Semantics decision S4) and nothing rests on it.
**Current status.** Stated, in the draft plan W1; to be checked sentence by sentence by a judge (log W2).
**Open question.** Which of the owner's six unknowns the theory as written cannot reach (plan prediction P1.2). An unknown it cannot reach is written here as an ask for the owner, never as a change to the theory.

## W-R2. The HV Skill is the judge the workflow calls, and the model places it
**Claim.** The skill carries the theory's Account check (Part V) and support tests (Part VI) for an agent at one call; the model of phase 1 says which of its tests need a target carried across calls (the same-explanation verdict, pairs that pull, the best rival) and which do not. The skill is frozen (file 33) and is not changed by this project.
**What this project asks of the HV Skill, when phase 1 freezes the model's word list:** one change to the skill's word list under that project's own plan, covering the nine loose rows and the eleven unmapped notions of its H69, and the reading of a job tagged *fixed* as a protected obligation (file 10, Part XI). Not before phase 1.
**Current status.** Stated (plan W1, section 12). The boundary between the skill and the planning work is HV RELATIONS R6, read only.

## W-R3. The Planning skill's loop is every phase's loop
**Claim.** Each phase of the programme is a numbered plan frozen with predictions as counts that could fail, run on the owner's word, read under frozen criteria, with a results file that names what it did not test (Planning file 2). The plan W1 is itself written to that skill.
**What this project asks of Planning, after phase 3:** whether an agent's arrangement (stateful, stateless, what it is handed at each call) belongs in `readers-and-markers.md` or in the workflow's arrangement; and the sorting of marked fields into within-step and cross-step, if prediction P3.2 holds.
**Current status.** Stated.

## W-R4. The Language project's checker is the one rule-signature component in the repository
**Claim.** A component whose relation is "invariant under interventions on the world and variable under edits to the rule" (file 10, Part II) is what the theory calls a rule application; the Language project's checker (fixed rules on s(CASP)) is the only component in the repository with that signature and no language model in it, and is the workflow's candidate for that place. Its scope contract (L64) is the form a skill's contract could take.
**Current status.** Stated (plan W1, section 6). Read only; nothing asked of Language.

## Not claimed
- That the five projects form one system now. This project is the one that would make them one, and it has not.
- That any agent belongs to the theory's classes. File 10: "It does not prove that any human, machine, institution, or lineage belongs to the classes defined. It defines the classes."
