Running the adapter in place is still the orchestrator's decision, as the harness worker's return says.

**Why the scratch-copy numbers are the harness's numbers for these marks** (seen, `checks/c5_inputs.py`):
- The marks are the saved files, unchanged.
- The rebuilt records feed only two things into the counts: each run's document (for `marks_per_part`'s document gate) and the four run-record fields.

**The size of the comparison, not a score.** 450 items were compared: 317 numbers, 31 verdicts and 102 lists. 96 of the lists name the disagreeing and the unreadable reports, field by field and set by set. 417 items match.

## 3. The discrepancies, each with its cause

### D1. `marks_per_part`: the gate counted by document (harness) or by report (independent). 4 items.

**What differs.**

| set | harness | independent |
|---|---|---|
| p52 | 6 of 16 documents, threshold 14 | 37 of 48 reports, threshold 40 |
| repeat | 0 of 2 documents, threshold 2 | 44 of 48 reports, threshold 40 |

Report by report the two programs agree exactly: 37 and 44 agreeing, with the same ten disagreeing reports and the same unreadable one in p52, and the same four disagreeing reports in the repeat set.

- **Explanation.** `stage_b.py` reads "marks_per_part read by document" as a count of the documents all of whose reports agree, against ceil(40/48 × the documents in the set). The independent reads it as a count of reports against 40 of 48.
- **What it forbids.** Any report on which the two programs' outcomes differ.
- **Rival.** The programs differ on some reports, and the document counts only show it.
- **Check** (seen, `checks/c3_marks_per_part_unit.py`). The independent's own per-report outcomes, grouped by document, give 6 of 16 and 0 of 2, which are `stage_b.py`'s numbers. c1 also shows the same reports named on both sides. The rival is ruled out.
- **Is it the same test at a coarser grain? No** (worked out by c3 from the document sizes).
  - In p52 (16 documents of 3 reports), the document gate passes with as few as 42 of 48 reports agreeing, and fails with as many as 45.
  - In the repeat set (2 documents of 24 reports), it passes only at 48 of 48 and fails at 47.
  - The texts' gate is 40 of 48, which allows eight disagreeing reports. In the repeat set the document gate allows none.
- **Classification: the texts admit two readings, and one part of the harness's reading is its own.**
  - *For the document count:* W3 section 7, which marking plan section 5 quotes, says "Agreement is a count of documents", and W14 section 2 says "`marks_per_part` is read by document as the plan says".
  - *For the report count:* marking plan section 4.3 glosses the very phrase: "W3 P3.2 requires the field be 'read by document', and it is: the map belongs to one report on one document and is never summed". The threshold is "40 of 48" in each set of 48, and neither set holds 48 documents. criteria.json's `marker_to_marker_rule` counts "over reports".
  - Neither reading is forbidden outright, but the plan's own gloss and the threshold's "of 48" weigh against the document count.
  - **The texts do forbid the harness's threshold as written.** The scaling ceil(40/48 × documents) is in no frozen text. c3 searched W14 for "ceil", "scaled" and "proportion" and found none of them, yet `stage_b.py`'s docstring lists the scaling among "Rules fixed in W14 before any mark existed". W14 section 2 says the consequences are "applied as written", and this one is not written. That part is a fault of the harness: it records as W14's a rule W14 does not contain.
- **Inside the harness.** `stage_b.py` counts the same field by report in its own W10.16 split: read n 20 plus unread n 76 is 96 reports. One program counts one field in two units.
- **Counts that change.**
  - The gate counts and thresholds above.
  - The repeat set's per-set verdict: by report it reaches 40; by document it misses 2.
  - **No certification moves.** p52 misses under both units (37 < 40; 6 < 14), so `marks_per_part` is struck either way, and P3.2 fails either way.

### D2. W10.16: which reports count as read, and over what base. 23 items.

**What differs.** The harness's split is over 20 read reports, with percentages over readable reports, and falls on `marks_per_part` (+18.7 points). The independent's primary is over 26 read reports, with percentages over all reports in the subset, and falls on `rivals_built` (+11.3). All 21 of the harness's split numbers equal the independent's own reading A computed over readable reports (c1's cause rows: 26 of 26 match).

- **Explanation: two readings of W14 section 3, and two bases.**
  - The read set. `stage_b.py`'s pattern takes the folder-qualified record file names ending in `.json` that appear in criteria.json and marking-plan.md: reading A, 20 reports. The independent's primary adds the six adapted run ids that marking plan section 14.1 writes directly: `p52_I2-m2`, `rep31_F4-m2-r1`, `rep31_P3-m1-r2`, `rep31_P3-m2-r2`, `rep_F4-m1-r2` and `son31_F4-m1-r1`. That is reading B, 26 reports.
  - The base. `stage_b.py` divides by agree + disagree. The independent's primary divides by all reports in the subset.
- **What it forbids.** Any difference in the agreement counts on the same read set and base.
- **Rival.** The programs pair or compare the marks differently on the read reports.
- **Check** (seen, c1's cause rows and `checks/c2_read_sets.py`). The harness's read set is exactly the independent's reading A, and its split numbers equal the independent's reading A over readable reports exactly. No folder-qualified name in these two files is written only without `.json`, so the harness's pattern loses nothing. The rival is ruled out.
- **Classification: the texts admit two readings, twice.**
  - *The read set.* W14 section 3 says "the record files named anywhere in `instrument/criteria.json` and `instrument/marking-plan.md` (placeholders like `X.json` excluded), mapped to run ids by set". W13 section 2, which W14 replaces for this purpose, says "the file names in the marking plan's sections 13 and 14 and any later section".
    - Both texts say file names, and "mapped to run ids by set" describes names that still need mapping, which a run id does not. So the words favour A.
    - They do not forbid B. A run id names a record file by the adapter's rule, W14 says "anywhere", and section 14.1 shows the fault-4 reports were in front of the reviewer and A4 while the key rule was reworded.
    - W14's purpose clause ("the reports any maker or reviewer read") cannot be the working rule on its own. Section 14's opening says the reviewer found fault 4 "by running the rule as a program over all ninety-six reports", which would make every report read and leave nothing unread.
    - W14's "anywhere" does forbid reading D (the marking plan's sections 13 onward only) as stage B's rule.
  - *The base.* "Agreement over the read reports", with unreadable counted as not agreeing, follows marking plan section 5: a gap is "never agreement". Dividing by readable reports follows section 14.2: a null "subtracts a document from rivals_built's denominator in stage B". Neither is forbidden.
- **Counts that change.**
  - The 21 split numbers.
  - The field W10.16 falls on. Under the harness's reading, `rivals_built` is +9.9 and not falsified. Under the independent's primary, `marks_per_part` is +5.6 and not falsified.
  - **The verdict does not change.** W10.16 fails under both programs, and under every one of the independent's five readings and both bases.
  - **No certification moves.** The field it falls on is struck by P3.2 under every reading. `pairs_that_pull`, the one certified field of the three, is not falsified under any of the independent's ten reading-and-basis pairs, nor under the harness's (c1's cause row).
- **What this leaves loose** (the qualified Derivation 3, applied to the split rule itself). Which field W10.16's consequence lands on ("certified on the unread reports only, or struck if it fails there") is held by the reading, not by the marks. It moves nothing here only because both candidates are struck already. The results file W15 has to name the reading it ticks under.

### D3. The two fields that are not candidates: a threshold and a certified flag. 6 items.

**What differs.** For `marks_outside_closed_list` and `layer_at_fault`, `stage_b.py` prints a threshold of 39 in each set and `certified: false`. The independent gives neither. The counts are the same.
- **Explanation.** `stage_b.py` takes `THRESH.get(name, DEFAULT)` for every comparable field, and certifies a field only when its `certified_candidate` is true.
- **What it forbids.** The harness certifying either field. **Rival:** the harness treats them as candidates. **Check** (seen, the saved `stage_b_record96.json`): both have `certified_candidate` false and `certified` false, and neither is in the certified list. The rival is ruled out.
- **Classification: the harness, presentation only.** The texts give these fields no threshold. The section 6 table names the fields at 39, and criteria.json says "false fields are read-outs and gauges and carry no arm difference". A printed `40/39` for `marks_outside_closed_list` in p52 reads like a pass. It moves no count and no certification.

### D4. The independent's stated reason for not counting the four run-record fields. No number differs.

- **The claim.** `output.json` says the four fields are not counted because "both sides are filled from one run record by program (record_adapter.py; first_marker.py collect), so any agreement on them is by construction". The README says the same.
- **Check** (seen, `checks/c4_run_record_fields.py`).
  - No raw mark on either side carries any of the four fields.
  - After collection, the first marks carry all four on 96 reports, and the second marks carry none: the second validate log names each one missing 96 times.
  - `second_marker.py` never calls the routine that fills them.
  - W14 section 1 itself says only "`first_marker.py collect` (the four run-record fields filled by program)".
