The owner asked, before any forced change is built, whether the method makes sense, and said to use five Opus agents armed with the hard-to-vary skill (33, the hardened version), each with a separate task. Done 22 September. The five reports are kept whole in "L76 Method review - five hard-to-vary reviews", with the brief they were given. Each read skill 33 first and worked read-only; three ran nothing, one (A3) ran the tools on scratch copies, one (A5) read the git history. Every claim below that is theirs is marked by its report; what is mine is marked as mine.

## The verdict, in one paragraph
The method's frozen plans, append-only log, hash-and-rerun checks and blind reader are real and did their work (A4, A5). But the method has let the same failure through four times: a claim about a thing written from a picture of the thing, not the thing. The fourth instance is in the list of forced changes I gave the owner at L75. So the answer to the owner's question is no, not yet: three things in the method must change before the new versions are built, and one of my four forced findings must be rewritten from the code. What follows is what the five found, checked against each other and against the code where they disagree with me.

## 1. Corrections to my own L75 list (A1, A2, A3, A4 all found these independently)
- **Finding 3 was wrong as stated, and the fix I proposed would not have worked.** I wrote that the driver prints the sentence "only in what-if and plan headings" and that one line would fix it. Four reviewers read the code: `describe_lines` (run_check.py line 47) prints "[mark, sentence N]" beside every line it lists, in eleven branches; the project's own smoke report shows it. What lacks a sentence is the head line of a BECAUSE, SINCE or PLAN finding and the two branches that list no lines at all, JUMP and NO CONNECTION. Those are exactly the seven findings the reader could not trace. And the four it did trace were traced from a sentence number the *translator* wrote into the ledger's `whose` field, which the driver echoes. So the fix is: a sentence on each head, a described-lines block for JUMP, NO CONNECTION and CANNOT TELL, and the same form in consequences.py, which prints no sentence at all. Lesson L10.
- **Finding 2 points at the print, not the rule** (A2). Astra Pro's own audit said the assumption-relative procedure can be coherent. Refusing the tie would switch patch 13 off for nearly every bare causal claim and bring F09 back from the other side. What must change: one sentence in 38 saying what a what-if answers (the writer's own causes taken at their word), and the report printing every line set aside, the BECAUSE that tied it, that BECAUSE's own verdict from the checks above, and the note 38 line 113 promises wherever a line used was filled in, which the what-if block never prints. F09 and this finding run through one function, `results_tied_to`; they are one joint and must be decided together.
- **Finding 4 is the driver's fault, not the tool's** (A2, A3): a module-level global, `WORLD_REMOVED`, that only `check()` sets. Fixing the tool leaves the trap for the next tool. The world should be an argument of `run_query`, which refuses to run without one. And K3 was the wrong warrant: no frozen expectation failed; the fault was found by reading the program.
- **Finding 1 is wider than told worlds** (A2): the driver strips every case line, so a BECAUSE inside a SUPPOSED case is never tested either. 38 promises only "a contradiction, or none" inside a world, so the driver conforms to 38; the clash is with L64's own tables, which put reported texts in scope and cite T10-D as the JUMP witness, a witness produced by my own September ledger that did not follow 39. Recommended: 38 and the driver move together, with a stated give-up: inside a world, a finding that needs a line from outside the world is counted, not reported.
- **Six findings force a change that I did not list** (A2, A3): NO FAULT FOUND printed where the question was never asked, which L64 line 145 names as an unacceptable error in the owner's own table; a sentence that reaches neither a line nor the bin while the gauge prints "0 of 3" (T10-B), which L64 line 142 names; the bin gauge that fires on 18 of 18 and cannot exceed... in fact can exceed its denominator (A3 ran it: "4 of 3 sentences"); the what-if's missing filled-in note; "nothing changes" printed where the program means "no change in the reported fact set"; and L64's section 8 trigger 5, which may have fired at L72 and was read away by my hand pairing, which treated TOLD and CLAIMED as the same content while finding 1 says they are not.
- **F15 is the readiest change in the record and I put it last** (A2). Its forcing case and control are written.

**A2, the forced changes.** Above. Plus a rival account of all four: they are one gap, between the question each check computes and the question its report claims. Nothing on the change list tells the rival from four faults, and the rival would put the read-back layer first. **A3, the instruments.** Every instrument takes the ledger as given; none reads the text beside the ledger, so all five read identically when the translator errs and the ledger stays consistent (T10-B). The gauge fails both halves of its poke pair (a lost sentence reads zero; a split bin entry doubles the reading). consequences.py measures the reporting, not the entailment: state a fact the ledger already derives and the derived count falls. sameness.py ranked a negation above the true match and hid the true match below its threshold; its buckets overlap. L71's E5 was an expectation the code guaranteed. The instrument that has done the separating on record is a fresh agent reading code and reports, and it appears in no plan and has no gauge. The variation test L64 line 143 names has never been run, and it is the one instrument that reads the text.

**A4, the test regime.** "Freeze the plan" and the "against" column are Claude's, not the owner's; three against cells did not bracket their predictions, so three misses fell outside them. L66 E2 and E3 were marked met on silence from ledgers with no said lines, against Lesson L2. E6 was marked against a threshold nobody set. The marking of E4, E5 and finding E rests on ledgers the worker corrected after seeing the run, while the frozen originals sit unmarked. L72's independence rests on the unchecked premise that a fresh Astra Ultra session carries nothing from its L66 session, which held results 37. Three of the four forced findings came from agents going past their briefs. The one cell that would have charged the language (L72 E1's against cell) did not fire. The fix for the recurring error is structural: a premise block in every plan, each premise a quotation from a named artefact with path and hash, and a second agent (Astra Pro) freezing the plan after a premise check. A4 also designed the next regime: two arms, one rerunning the ledgers in hand on old and new rig, one on ten new short texts in matched pairs, with the worker no longer running what it translates and the reader given old and new reports unlabelled.

## 3. Where the five disagree, and my reading
- A2 says finding 4 is not a K3 refutation; A3 says the gauge's wrong reading is the same kind of fault as finding 4 and should be counted the same way. Both are right about what they say: no expectation failed in either case, and both are instruments giving wrong readings. I take A3's line: a wrong reading from an instrument forces a change to the instrument, whether or not a frozen cell caught it; and I take A2's correction that citing K3 for it was borrowing authority.
- A2 recommends the driver for finding 1 with 38; A1 recommends first a column in L64 section 4 saying which findings apply inside a world. They are the same change seen from two files: the column is the contract term, the driver is its keeping. Both are needed and the column comes first.
- A4 would keep the plan-freeze; A5 shows the freeze's receipt (a commit hash) can be voided by a rebase. Both stand: freeze by hash of the file, not by commit.

## 4. What changes in the method before anything is built (mine to do, done at this entry where marked)
1. **A premise block in every plan**, each premise a quotation from a named artefact with its path and SHA-256, and no prediction that names an instance the key covers. **A second agent freezes the plan** after a premise check; the freeze is recorded by the plan file's hash. (Convention; applied from the next plan.)
2. **A second marker.** Every results file's marks are re-derived by a fresh agent from the plan and the outputs alone, and the two markings compared. First use: L72, as A5 proposes. (From the next results file.)
3. **Decisions carry the gloss marked as mine**, beside the owner's words, per Lesson L3. (Done for L7, L8, L9 at this entry.)
4. **Lessons state the occasions each fix covers**, and each new plan opens by naming which lessons' obligations it meets. (Applied from the next plan.)
5. **Tools are versioned like numbered files**: a new version is a new file beside the old, with a give-up line. install_scasp.sh and consequences.py were overwritten this week; the overwritten versions are recoverable from git and are named in Lesson L11. (From now.)
6. **Status corrected** where A5 found it stale or false, with dates. **READ ME FIRST** read order reaches L64, names the four error sources, the two agents, and the terms. (Done at this entry.)
7. **A table beside L64 section 4**: for each check the driver runs, the question it computes and the question the report claims, and whether it is asked inside a told world and a supposed case. I draft it; the owner strikes. (Drafted below as "L77 Table - what each check computes and what it claims", for the owner.)
8. **Give-up columns** on every forced change, both for the fix chosen and the rival fix, before it is built (A2). (In the build plan.)
Amendments A5 proposes to RESEARCH-CONVENTIONS.md (when a not-yet-sent file may be corrected in place; tools are numbered files; a commit hash is not a freeze receipt) are for the owner; that file is outside this folder.
