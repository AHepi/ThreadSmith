Only cases where something failed while being made or tested, and how it was fixed.

26. Both clauses Claude wrote for round 4 had faults that Claude's own checks missed and the other model found: one conflated "loose" with "fitted"; the other stated its passing condition on the outcome alone, which the thing it was meant to exclude also met. Fix: revised clauses for round 5, and a line in the skill: run any test you write on the thing it is meant to catch and on its nearest innocent neighbour.
27. The first draft of prompt 30 contained one negative word in an instruction ("when they cannot"). Caught by the program that searches each prompt for negative wording. Fix: reworded as "when either one is missing".
35. The judgement-phrase pass written into file 30 could be passed by any phrase at all: it asked for one change showing "met" and one showing "unmet", and far-apart changes are always available. Shown on first use: zero marks in 32 rows, and both phrases already known to rest on judgement passed. Fix: each pair is held against a near case (file 41).
49. File 41 asked the other model to build a tighter pair for any row the near case left open, and gave one example of the form (water present, beside tank at least half full). For O4 it built a pair that adds a controller to the index display, which distinguishes a controller from a passive display and leaves the disputed question, whether a measured regularity is an explanation of production, where it was; the model saw this itself and withdrew its first mark. The theory already holds the distinction that places O4: a production question's contract holds interventions on the upstream part, an identification question's contract holds edits to the observed value, and the two are different questions. File 41 did not point the model at that passage, so it invented a mechanism instead of using the theory's own. Fix: file 55 quotes the distinction in plain words, asks the model to find and quote the passage in its copy, and to build the pair from it, marked separately (PLACED BY THE THEORY'S OWN DISTINCTION) so a row placed that way is never counted as one the pass placed.
50. File 55 told the other model that if a faithful table fails none of the four conditions, "that is a finding against the theory's stated claim, and belongs at the top of the report". That sentence was written from the attack list in Part 0 alone ("lookup tables ... all fail one of the four"). Part V, further on in the same document, already says that a table genuinely encoding an organization's response to every admitted change "is not a table in that sense and is not excluded". The model found the qualification, said so, and still put the finding at the top, because the instruction said to. The finding is about one front-matter sentence, and the instruction inflated it. Fix: file 57 asks for the finding restated at its size beside both sentences; the rule is that before an instruction names a claim of the theory as a target, the whole document is searched for that claim's own qualifications, which is now possible because file 10 is in the repository (log 56).
S1. The script that updated the navigation files stopped on one line whose text had changed, and the commit and push that followed it in the same command went ahead anyway, so a commit reached main with the root README changed and the Semantics README, INDEX, LEGEND and the rest untouched. The chain joined the git steps with "and" but the script ran as a separate statement, so its failure stopped nothing. Fix: the edits were finished in the next commit; the rule is that a script whose success the commit depends on runs first, in the same chain, so that its failure stops the commit.

S2. The two-stage instructions carried the round's expected answer in the part the agent reads: S72's named O24 and O48 as the rows to find, S76's carried the frozen prediction and the pack carried S75 and the earlier audit's sampling sequence; the audit instruction printed Stage 1's verdict before the auditor's own reading; and S75 attributed to the instruction a SAME rule the tested agent had written after the data. Found by the five-reader review (S78), each item checked against the files. The rule: a prediction is frozen in the record and kept out of the tested agent's pack; a second reader writes its reading before it opens the first reader's; the rule that decides a mark is written into the instruction before the run, and a rule adopted after the data is recorded as adopted then.
S3. Fix: the checker was stopped before it wrote anything. Rule: when a repository holds several projects, name the project and its last log entry back to the owner before starting work.
S4. Asked which "next language testing stage" was meant, the owner picked the Language option and then sent "Whoops", "No", "Yes I did", "No no I meant semantics" in quick succession. Claude acted on each message as it arrived: it started work in the Language folder twice and recorded a decision there. Rules: when the owner's messages contradict each other within a minute, wait for them to settle before acting outside this folder; never chain an amend after a command whose result has not been read.
S5. S80 and S81 were numbered from this project's own entries (S79, then S80); LEGEND's rule gives the shared sequence's next number, which stood at L86, so S87 and S88. Found by the S81 builder after S80 was running. Fix: names kept, the deviation recorded in log S80. Rule: read the highest number across all three projects' logs before naming a new entry.
S6. The first S80 design compared the skill (13,648 words and an instruction to use it) with a one-line system prompt, and its task named two of the skill's own target kinds to every reader; both would have made the result unreadable. Caught by the outside cross-examination (Atria and Mimo, both RUN WITH CHANGES), not by Claude's checks. Fix: a length-matched placebo method under the same framing, and a neutral task. Rule: a treatment that is a long text is compared with a text of the same length, and the task names nothing the treatment supplies.
S7. S80's probes and pilot used tiny prompts, or one provider with thinking off. At the real size (a 33,000-token system prompt, thinking at high effort) Mimo spent its whole 64,000-token budget on reasoning and wrote no report, on every skill and placebo run (six of six failed after three attempts each). Fix: the runs were paused; Mimo is to be rerun with a larger budget. Rule: pilot each provider at the full prompt size and full effort before a counted run.
S8. A probe of the second S80 version hung for eleven minutes: a stream stayed open without going silent long enough for the idle timeout to fire. Fix (the builder's): a total deadline on every stream as well as the idle timeout. Rule: every network call has a deadline on the whole call, not only on silence.
S9. The S81 contamination check voided all six Sonnet returns. Two causes: the harness's own report hand-back tool was counted as a tool outside the folder, and the word "prediction", listed as a leak word, is an ordinary word in the theory and the case book, which every honest reader paraphrases. The synthetic test had used made-up transcripts and words, so neither showed up. Fix: the hand-back tool exempted, and each hit read and cleared by Claude with the reason in the receipt; the first judgements kept under new names. Rule: test a contamination rule on the real texts and a real transcript before the run, and choose leak words that do not occur in the material the reader is given.
S10. Two S80 runners shared the providers without a shared limit: the reader run held three Mimo slots while the S81 audit needed them, and the per-provider limit of three (decision S12) holds only within one process. Fix: the S80 run was paused (it resumes where it stopped) before S81's calls began. Rule: one runner per provider at a time, or a lock shared across processes.
S11. Lesson S7 was written and then repeated within the hour: the S81 blind reading (12,740 words, no system prompt) was sent to Mimo at the same 64,000-token cap, and Mimo again reasoned through the whole budget (219,000 to 286,000 characters of reasoning) and wrote nothing, three attempts running. The cap came from the shared reader ladder, which nobody changed after S7. Fix: a separate cap for Mimo at its ceiling, 131,072 tokens (probed: 200,000 is refused), in `tools/s81_build.py`. Rule: a lesson about a setting changes the setting everywhere it is used, in the same commit.
S12. Twice a test went out before the rule for reading it was written. The S81 effort controls were sent at 11:11 UTC with a statement of purpose and no reading rule; the rule was written at 11:28 to 11:29, after the Mimo control had returned (11:27:49) and before anyone opened it, and the commit that carried it (10464ba) was titled "reading rule written before their data", which claims more than happened. Then the S88 cross-examination was sent at 14:07 with no reading rule at all; Atria's reply arrived at 14:24, and the rule was written after it arrived and before it was opened. Both times the data waited unopened, so nothing was read in order to fit a rule; but a rule written with a reply on disk is written knowing that the reply exists, that it came back, and when. Found by the process audit (the controls) and by the orchestrator (S88). The supplementary audit of Mimo on tester A and the S87 cross-examination, sent the same day, went with their rules written and committed first, which shows the order was available. Fix: each late rule states in its own text when it was written and what existed by then, and every report of the data it governs says so; S81 Results records that the commit message overstates. Every brief sent after 15:36 went with its rule committed first (Mimo's S88 parts, Mimo's S87 parts and one-row retry, the S90 brief and its five parts, and the seven calls rerun after the container restart), but the runner still has no check that refuses a brief without one. Rule: a brief and its reading rule are written and committed as one step, and the launcher refuses to send a brief whose reading rule is not committed; a record says "before the data was opened" when that, and not "before the data", is what happened.
S13. Medium effort was accepted by both providers and did not bind where it mattered. The pilot sent "Reply with the single word READY." at 4,000 tokens and showed only that "medium" is accepted. At full size, Mimo's audit of tester A's 52 rows reasoned to its 131,072-token ceiling and wrote nothing on all three attempts at medium (540,000 to 554,000 bytes of reasoning each), as much as the two attempts at high that ran to the same limit (557,000 and 570,000 bytes); its audit of tester B's return, the same task on the other tester's reading, finished at medium. Pass 2 was the last pass the plan allowed, so the audit is missing from the round, and the crossing it carried is lost on tester A. (Atria's medium effort control also ran to its 65,536-token limit on all three attempts; by that control's own reading rule, R4, a failed control supports no inference about effort.) Fix: the audit's rows split into four parts of thirteen, sent as a supplementary audit outside the table, under a reading rule written first; two of the four came back (log S87). Rule (extends S7): a setting that is accepted is not a setting that binds; before the last allowed pass, pilot each provider at the counted run's full size and effort, or send one counted call first and read its token use.
S14. The first runner handed back before its run ended. A Claude subagent was told to send the pending S81 pass-2 calls, wait for them and commit the outputs; it launched the run at 11:11 UTC and ended its turn about a minute later, and the harness then asked it for its report, while the run went on until 13:39. For that minute on, nothing inside the session was waiting on the run's end. Fix: the orchestrator stood the agent down at 11:15, and a watcher outside any agent, on the run's process, reported its exit; the returns were checked and committed after it (6106e7d). Rule: a long run is watched by a timer outside the agent that starts it, and the agent that starts it hands back as soon as the run is launched, saying what the watcher waits for and what is to be done when it fires.
S15. The frozen S81 plan was changed repeatedly without a third version. The second version says of itself: "Frozen once the first agent or call of this version is started; a change after that is a third version." After its first agent started, the testers were changed (decision S16), the output limits raised, the effort lowered for the pending calls (decision S17), a cap on passes coded, effort controls added and the log entry renumbered; and one read-me reinterpreted the plan's "thinking on (`reasoning_effort: high`)" as describing pass 1, in place of recording a change. None of this had a third version until the process audit found the gap at about 11:25 UTC. Fix: the third version (24d2d75, written at 11:33, before any pass-2 return), giving for each change the second version's words with their line, what was done instead, on whose authority, and whether it came before or after the data it could bear on. Rule: a change to a frozen plan is written as the plan's next version in the same step as the change, and before the call the change governs is sent.
S16. The owner's "Use Atria and Mimo on medium thinking effort for cross examination" (decision S17) was made one global setting, which reached every tool and every provider: the S80 readers, test subjects under a frozen design that had run at high, the S80 markers, and DeepSeek, which had never been piloted at medium. S20. Large single calls to the outside models kept failing, and each was split only after it had failed. Mimo's audit of tester A (36,690 words, 52 rows) ran to its 131,072-token ceiling with no answer on all six attempts, at high and at medium (lesson S13), while its audit of tester B, of the same size, finished. Mimo's single S88 call (13,510 words: three findings, their repairs and a hunt for more) failed at 17:40 UTC, two attempts to the ceiling and one cut short, none with a reply. Mimo's single S87 call (25,477 words: seven rows and three further tasks) failed at 19:24, three attempts to the ceiling and three disconnects. Atria's single S90 call (25,790 words: 48 changes) failed at 21:20, four disconnects and two attempts to its 65,536-token ceiling. Split by finding, the three S88 parts (about 10,000 words each) all came back. Split by rows, the supplementary audit (the same 36,671-word text, thirteen rows a part) came back on two parts of four, one attempt ending on the provider's content filter; the S87 parts (about 16,000 words, two or three rows each) came back on one of three, and that one used 106,392 reasoning tokens against its 131,072-token ceiling. Split one row per call, the three S87 retries all came back; split by group of changes into parts of at most 18,000 words, all ten S90 part calls came back; seven of those thirteen came back only on a second pass, after a container restart had cut the first (lesson S24). The number of words did not predict failure (13,510 failed; 37,701 finished); the reasoning the task demands did: how many findings, rows or changes it holds, and how hard each is. And the lesson of one failure was not applied to the next: the S90 brief was built as one 25,790-word call at 19:01, after Mimo's S88 call had failed whole at 17:40 and its split had come back by 18:49. Found by the receipts, and by the orchestrator. Fix: each failed call was rebuilt as parts under a note written before sending (S88 by finding; S87 by rows, then one row per call; S90 by group of changes, each part to both models), and every call so rebuilt came back in the end, and decision D11 cuts the revision 2 round's auditor briefs to at most 13 rows a part. Rule: size a call to an outside model by the reasoning it demands, not by its words; split it by finding, row or change from the start, into parts small enough that fitting under the ceiling is the expected outcome, not the lucky one; and once a split has worked for one call, build the next call split.
S21. Disconnects spent the attempts. In the receipts of every S81, S87 and S88 call to Atria and Mimo, 23 of 73 attempts returned no HTTP status at all (Atria 7 of 20, Mimo 16 of 53), and the failed single S90 call adds 4 of its 6. Eight of Atria's eleven ended at 1,802 to 1,803 seconds, which points to a cut at thirty minutes somewhere between the machine and the provider; the cause is not established. All of Mimo's came after 15:00. The runner allows six attempts and counts against its limit of three only the answers that come back and fail, so a disconnect spends an attempt without counting as a failure: S87's part P3 made six attempts, five of them disconnects, and failed with only one answer ever returned, and that one empty; part P1 lost four of its six to disconnects before its one full answer ran out; Atria's S87 reply came on its third attempt, after 57 minutes of disconnects on the first two. The S90 parts bore it out: Atria's reply to part A2 came on its fourth attempt, after three disconnects of about 1,802 seconds each, and in the second pass after the container restart Atria's three calls lost 10 of their 15 attempts to disconnects, part C being accepted on the sixth and last attempt its pass allowed. Each disconnect near thirty minutes holds a slot for half an hour. Found by the receipts, read for this record. Fix: none in the runner yet; the rows of the failed parts were sent again in smaller calls (P1 one row per call). Rule: budget attempts and time for disconnects as well as for rejected answers: count the two apart, allow enough attempts that a run of disconnects cannot use up a call, and plan a round's elapsed time for about one attempt in three lost.
S22. The owner's limit of five Claude subagents at a time (decisions S12 and S17) was kept by the machine, not by Claude. The orchestrator launched its subagents through the machine's workflow runner and relied on that runner's own cap on concurrent agents, a number Claude did not set, instead of keeping a count or lock of its own. The process audit reconstructed at most five up to 11:25 UTC from the transcript; nothing counts after that, so whether five was ever exceeded later is not established from the record. The outside calls, by contrast, had an explicit lock from 14:05 (three per provider across processes, f5f9dcb), and the runners' logs show calls waiting on it. Found by the orchestrator, reviewing its own process for this record. Fix: none yet in the tools; the gap is recorded here and in log S87, and a count or lock at the owner's number is owed before the subagents of the revision 2 round are launched (the project story's Next step). Rule: a limit the owner sets is enforced by a count or lock that Claude sets to the owner's number and can show afterwards, as the slot lock does for outside calls; a cap that happens to exist on the machine is not the owner's limit.
S23. Committed records cited working files that were only in the session scratchpad. The S88 brief (13:51 UTC) was built from three checks that stayed in the scratchpad until 16:07, and the reading of Atria's reply read them there under their scratchpad names; the revision 2 worklist and plan pointed into the scratchpad for the source audit and the candidate cases until the same commit (b6aba4c). Still outside the repository: the working files the revision 2 change list says it was assembled from (the decisions as taken, the item skeleton, the five entry files and the two adversarial checks). D3-T's prompts, author returns and agreed text, the case the revision 2 plan enters as O76, were in the scratchpad only until 22:58. The scratchpad belongs to one session and can be lost (the revision 2 plan's risk R7). Found by the revision 2 plan (R7, D10) for the first group, and in writing this record for the rest. Fix: the first group was committed at 16:07, each file with a header naming the scratchpad path it came from (D10); D3-T was committed at 22:58 (09193e7), with a read-me saying where its files were made; the change list's working files are named here and in log S90, and are to be committed before revision 2 is frozen. Rule: a working file goes into the repository in the same commit as the first record that cites it; the scratchpad holds nothing a committed record depends on.
S24. A container restart cut the network for runs already going. The container restarted at about 23:30 UTC on 23 September while two runners were sending calls, the S90 parts run and the S87 retry run, both started before it. They kept the agent proxy address they were started with, and after the restart the proxy was at another port: the attempts in flight of six calls lost their connection, a seventh call's attempt was refused as it started, and every later attempt was refused at once. The runner counted each refusal as a failed attempt, and its back-off used up the six attempts of all seven calls (Atria's parts A1, B2 and C, Mimo's parts B2 and C, and the S87 rows O5 and O30) within about six minutes: the seven ended as failed between 23:33 and 23:37 with no reply, on nothing any model did. Found by the orchestrator after the restart, from the error files, each ending "Unable to connect to proxy" (1feb425). Fix: a note written before sending (`results/S90 and S87 - seven calls rerun after the container restart - written before sending.md`, 57482a5) ruled that a failure caused by the session's own network is not a reply from the model and does not use up the call; the seven went again as pass 2 from a shell started after the restart, with requests byte-identical to pass 1's and no pass 3 (faf91f6), and all seven were accepted (286d69c). The three replies that had come back before the restart were intact, each matching its receipt (c137e86). Rule: after any restart, check every runner that was going and relaunch, from a shell started after the restart, every call it had not finished; a proxy or connection failure is not a reply from the model and is not counted against the call; the rerun goes under a note written before sending.
S25. Two rulings on one change were written to the same file name, and one was lost. In S90's batch 1 (23 September, from about 23:05 UTC), Mimo's reply to part A2 contested change R51 twice, in its point 3 and in its task (d) paragraph, and each went to its own fresh checker; both checkers were given the same file name, `ruling s90_xexam_mimo_A2 R51.md`, and when the batch was recorded the one file there was the point-3 ruling. The task (d) ruling survived only as the orchestrator's summary, cut off at its end, which said that "the exact text" of the CHECK line "is in the ruling file". Found by batch 1's recorder, who recorded the ruling from the summary and marked the file as missing (fbcef8c). Fix: in batch 2 the checker of Atria's reply to the same part ruled R51 again, and its CHECK line covers both replies (8263ff9); from batch 2 on, each ruling file's name carries the call and the item number (`ruling <call> item <n> <change>.md`); and the draft-3 pass took every ruled text byte for byte from the ruling files and the readings. No outcome was lost: all three R51 rulings are KEEP with no text change. Rule: every output file name is unique per item, naming at least the call, the item and the change; a task that hands several writers work on one change gives each its own name, and a writer never writes over a file that already exists.
