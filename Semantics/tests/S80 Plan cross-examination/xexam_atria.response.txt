Cross-examination of plan S80. Each point: what is wrong, why it matters for the question "does the skill add anything or should it be abandoned", and the smallest change that fixes it.

**1. The no-skill arm is not the deployment comparator, and it is ~13,600 words shorter.**
The plan says the project's actual use is "readers armed with the skill, the other model given file 24 in its place" (S78). But the runner uses `reader system - without skill.md` — one line, "You are reviewing a document." — while the skill arm gets a 13,648-word system prompt *plus an explicit instruction to use it*. So the measured contrast is not "skill vs no skill" but "long method document + method instruction vs bare instruction." Both directions of bias are live: the length/instruction alone could raise thoroughness and item counts (false positive for the skill), or the absence of any method framing could depress performance in a way the skill's content would not (false negative). Either way "abandon" and "adds something" are both uninterpretable.
*Smallest fix:* replace the one-liner with a length- and instruction-matched placebo — file 24, or an irrelevant method text of similar size, prefixed by the same sentence ("You have the method below… and you should use it for this audit"). If a placebo arm is too expensive, at minimum run file 24 as the no-skill comparator, matching S78.

**2. The reader task hands every reader the skill's target categories by name.**
`reader task.md` tells all readers to look for "conditions or clauses that do no work" and "anything that shields the theory from criticism" — exactly the two HV kinds. The plan does this deliberately so no-skill readers "are not left to guess," but that *is* the guessing the skill is supposed to remove. The no-skill arm is partly taught the skill's targeting, biasing the result toward the null: a null then cannot distinguish "the skill adds nothing" from "the task prompt already supplied the skill's key content."
*Smallest fix:* delete those two phrases from `reader task.md` for all arms; keep only the generic taxonomy (false statements, failed proofs, claims wider than support, contradictions). Optionally add a second task variant as a sensitivity arm.

**3. Markers mark their own model's reports, and skill-style is an unblinded pathway to the verdict.**
Atria marks Atria's reports, Mimo marks Mimo's. Self-marking bias is not addressed anywhere (the plan only discusses style leakage). With the "both markers say FOUND" rule, a marker that is lenient toward its own model's habits systematically shifts that reader's row, and the two markers' biases do not cancel across the agreement table. Separately, the skill changes a report's vocabulary ("held", "loose", "idle"), and markers may know the skill — so condition → style → marker recognition → verdict is a real, unblinded route from the treatment to the outcome, which the "Found when" rules only partially block.
*Smallest fix:* skip marking jobs where the marker's model is the report's model (each report still gets two non-self markers); add to `marker task.md` an explicit instruction to ignore the report's vocabulary or method and mark only by the key's rules; extend the Opus adjudicator to *all* disagreement cells (found-flag disagreements *and* GENUINE/MISTAKEN/UNCLEAR splits), and have it re-mark a random 10% sample as a drift check.

**4. The Opus arm's leak is bigger than the plan says, and Opus still counts toward the decision rule.**
The plan admits the seeded file sits in `tests/` under its S80 name and the repo is "in reach," and mitigates by searching each Opus report for "S80"/"seeded"/"planted." That catches *naming*, not *use*: an agent with repo access can diff the clean and seeded documents in either condition. In the clean condition it can then "find" planted errors that are not there — invisible false alarms that no keyword search will detect, in the arm that is supposed to measure false alarms. Also, Opus's thinking is unrecorded ("as the agent runs") and it has only two cells, yet it counts as one of the "four readers" whose same-direction agreement triggers a finding.
*Smallest fix:* run Opus in a sandbox containing only the working folder, with the document copied in under a neutral name ("document.md") and no repository access; log and inspect the agent's tool calls, not just the report text; record the thinking setting per run; and require the "two readers" in the decision rule to be API readers with matched thinking contrasts (Opus reported separately).

**5. Three repetitions cannot support the stated decision, and no uncertainty is quantified.**
Each cell holds 12 opportunities per error kind. A difference of one error is ~8% and, as the plan concedes, noise — but nothing replaces it: no confidence interval, no test, no multiplicity control over 4 readers × 2 thinking settings × 2 error kinds, and the "same direction on at least two readers" rule has an unexamined false-positive rate. The 2×2 design is also claimed to "separate the skill's effect from thinking's," but with n=3 the skill×thinking interaction is effectively unidentifiable at useful precision.
*Smallest fix:* report an exact binomial or bootstrap CI for every contrast, and call a finding only when the CI excludes zero and the sign agrees on ≥2 API readers; pre-state the numeric decision rule; explicitly mark the interaction as exploratory. If budget allows, raise reps on the two decision cells (ST/NT, SO/NO) first.

**6. The false-alarm metric is mis-specified and unnormalized.**
False alarms are counted only on the clean document — the no-signal condition — and compared as raw counts against found-errors-out-of-24. But the skill changes report *form* and length (its own prior test found so), and "false alarms not rising by more than the gain" has no denominator: a skill that doubles items listed doubles raw false alarms while adding one find, and would be rejected on a verbosity artifact. Also, false alarms while real errors are present (the real deployment condition) are already marked but never reported — the markers already judge every non-key item on the seeded document.
*Smallest fix:* report false alarms per listed item (rate) alongside raw counts; add the seeded-document MISTAKEN count to the table as "false alarms under load"; define the accept/reject threshold in rates, not raw counts.

**7. There is no verification or aggregation code, and several failure modes are silent.**
Nothing checks completeness: a cell that fails with a non-retriable status (400/413 — plausible for an unprobed `reasoning_effort` field, or a payload-too-large skill prompt) is simply absent from the results and would enter a hand-built table as a low score. Nothing checks truncation: the "END OF REPORT" sentinel is never validated, and a non-empty response that hit `max_tokens` is saved as a success. Nothing checks the documents' md5s at run time, so a later edit to file 10 silently changes the clean arm. The key file is sliced by heading strings (`key.index("## The error file 10 already carries")`), which raises `ValueError` if the headings differ and silently mis-slices if they are in the wrong order. Marker JSON is never schema-validated, and the final table is built by hand. Finally, the key becomes public inside the repository as soon as `mark` writes marker `.request.json` files, so any later `readers` rerun — or a late Opus run — could see the answer key.
*Smallest fix:* add a `verify` command (all 84 reports present, END OF REPORT present, md5s match, marker JSON parses, every key id present) and a `table` command that joins marks with MAP.json and applies the agreement rules; assert the key's structure before slicing; refuse to run `readers` once any marks exist.

**8. The owner's decision contrast is ST vs NO, which changes two things at once.**
Decision S12 names "thinking on with the skill, thinking off without the skill" as the comparison. A gain in ST–NO is not evidence about the skill: it is skill+thinking vs nothing, and can be mostly thinking. The plan does read the matched contrasts too, but the decision rule should not be allowed to fire on the confounded one.
*Smallest fix:* make ST–NT and SO–NO the decision contrasts and report ST–NO as descriptive only; add the caveat that SO–NO is a lower bound (a 13,000-word method plausibly needs reasoning to apply), so a null at thinking-off must not count toward "abandon."

**9. Runner robustness details that will cost cells or time.**
(a) Empty content with `finish == "length"` is retried five times then failed — plausible when reasoning tokens count against `max_tokens` under `reasoning_effort: high`, wasting ~10 minutes per affected cell and dropping it. (b) `reasoning_effort: high` is unprobed per provider; a 400 on that field is in `FINAL` and kills the whole arm without retry. (c) A worker exception (e.g., marking a report whose `.response.txt` is missing) propagates out of `f.result()` with no `.error.txt` written and no record beyond stderr. (d) `MAP.json` is written non-atomically, so two concurrent `mark` processes can clobber it.
*Smallest fix:* probe each provider's acceptance of `reasoning_effort` before the run; on empty+length, retry once with doubled `max_tokens` and record it; catch worker exceptions and write `.error.txt`; skip-and-report missing inputs in `mark`; write `MAP.json` via tmp+rename.

**10. Cross-reader comparability is assumed, not established.**
The "same direction on two readers" rule treats Atria, Mimo, DeepSeek and Opus as replicates, but they run at provider-default temperatures that differ, and Opus has no thinking control. The plan's "Not tested: temperature" is honest, but the decision rule should not aggregate over non-exchangeable readers without acknowledging it.
*Smallest fix:* restrict the agreement rule to the three API readers, report each reader's CI separately, and note provider-default temperature as a limitation on cross-reader consistency in the results.

One claim the plan cannot make good on: "the clean document measures false alarms." It measures false alarms *when there is nothing to find* — a different behaviour from auditing a document that does contain real errors (point 6). And "the four cells separate the skill's effect from thinking's" is a design statement, not something three repetitions can deliver at decision-grade precision (point 5).
