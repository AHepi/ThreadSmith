# Cross-examination of S80

**1. The Opus arm can derive the answer key from what is in its reach.**
*What is wrong:* The Opus subagent "has the repository in reach," which contains both `tests/S80 Seeded authority - file 10 with eight planted errors.md` and `authority/10 ... standalone theory.md`. A diff of the two files returns the eight planted errors exactly. The logs (S70âS75) also name D3 and its nature. The leak check â searching reports afterwards for "S80", "seeded", "planted" â cannot detect a diff-derived answer: a report that parrots the eight differences never needs those words. The document copy's filename in the working folder is never said to be neutral either; if the S80 filename travels with the copy, "eight planted errors" is on the label. *Why it matters:* one of the four readers in the decision rule ("a finding on two or more of the four readers") would be answering a different, trivially solvable task, inflating its founds in both cells unpredictably (the no-skill agent has more reason to go looking), and its reports feed the marking and the D3 column. *Smallest change:* give the subagent a working folder **outside the repository**, containing the document under a neutral filename (and the skill files for S), with no repo access; extend the contamination search to "D3", "Derivation 3", "S70"â"S75", "file 10", and pre-state that any hit voids that repetition.

**2. The reader task teaches the no-skill arm the skill's own taxonomy.**
*What is wrong:* The task tells every reader to look for "conditions or clauses that do no work" and "anything that shields the theory from criticism it should face" â two of the four HV kinds â plus "claims wider than their support." Half of what the skill is written to contribute is handed to the baseline in the prompt. *Why it matters:* it steals the treatment. The test can only measure the skill's residual value over a checklist of its own categories â which biases the headline decision toward "abandon" precisely in the case where the skill's value is "it tells you what counts." A null result would not license abandonment in real use. *Smallest change:* replace the category list with a neutral one ("false statements, invalid proofs, unsupported claims, contradictions, and any other defects"), and record in the plan that this is the comparison being made. (If real use does name the kinds, run the wording as a second factor on one reader.)

**3. No placebo: the contrast is 13,648 words plus "use this method" versus one line.**
*What is wrong:* The skill arm gets a huge system prompt *and* the instruction "you should use it for this audit"; the control gets "You are reviewing a document." Content, length/attention cost, and effort-demand all vary together. *Why it matters:* a gain cannot be attributed to the skill's content; a null can be a wash between helpful content and the attention cost of 13.6k words â which would produce a wrong "abandon." The plan's question ("does the skill add anything") is not answerable from a package-vs-nothing contrast. *Smallest change:* one placebo arm at the decision contrast (ST and NO): a length-matched neutral text under the same "you should use it" framing. If runs cannot be added, the verdict must say "the package vs. nothing" and cannot conclude "abandon" from a null.

**4. Truncated, filtered, or half-streamed output is accepted as a complete report.**
*What is wrong:* In `s80_call.py` any 200 with non-empty content is written and counted â including `finish_reason == "length"` (content cut at `max_tokens` mid-sentence) and mid-stream disconnects where `finish` stays `None`. `_stream` also silently `continue`s on any chunk that fails `json.loads`, losing that delta without trace. Markers have the same problem at 32,000 tokens: a truncated JSON mark is accepted and then simply unusable. *Why it matters:* truncation is correlated with the treatment â the skill's one established effect is to lengthen and restructure reports, and `reasoning_effort: high` competes for the same token budget in thinking-on cells. The comparison is biased against the very conditions under test, silently. *Smallest change:* accept only `finish_reason == "stop"` (reader reports must also carry "END OF REPORT"); anything else is a failure to retry with a raised `max_tokens`; count dropped SSE chunks in the receipt; validate that marker output parses as one JSON object.

**5. The counting rules contradict each other, and every uncertain item is dropped from the false-alarm side.**
*What is wrong:* The plan says a find counts "when both markers say FOUND" and a false alarm "when both markers say MISTAKEN," *and* that the Opus adjudicator's call "stands for the agreed table's disputed cells" â two incompatible counting functions. Under the conjunction rule, UNCLEAR items and unresolved disagreements vanish; the direction of every omission is "not a false alarm." False alarms are also counted only on the clean document (3 reports per cell), while gains are counted on seeded reports as errors out of 12 â different documents, denominators and units (items vs. errors) compared in one trade-off ("false alarms not rising by more than the gain"). Seeded-report false alarms are never counted at all. *Why it matters:* false alarms are systematically understated by an amount that can differ by condition (a hedging, item-spawning style produces more UNCLEAR), so the "gain bought with false alarms" verdict is unreadable and biased toward keeping the skill. *Smallest change:* write one counting function now: FOUND = both markers, else adjudicator; false alarm = both MISTAKEN, else adjudicator; UNCLEAR and adjudicated cells reported in their own columns; the trade-off computed as rates per report (founds per seeded report vs. mistaken items per report, clean *and* seeded).

**6. The outcome measures are form-sensitive, and the skill's only proven effect is on form.**
*What is wrong:* "Items listed" and false-alarm counts depend on how a reporter chunks its complaints (one merged item vs. twenty); FOUND requires "the right Part, sentence or formula," so citation style is graded; the skill is known (its results file 54) to change exactly these things â marks used, structure of report. *Why it matters:* the study can measure the documented form change and mistake it for detection ability, in either direction. *Smallest change:* make the locator rule substance-based (any unambiguous quote or unique phrase locates; style of reference is ignored), and report false alarms per report and per 1,000 words alongside raw item counts.

**7. Marking is blind to the label but not to the condition, each marker grades its own model, and the adjudicator grades its own family.**
*What is wrong:* The plan concedes the skill's vocabulary ("held", "loose", "idle") shows in reports â but here style *is* the condition, so the markers know which arm a report is in exactly where it matters. Atria marks Atria's reports and Mimo marks Mimo's, with self-recognition possible. The key labels each error HV or GEN, signalling which errors the skill targets. The adjudicator is Opus 5.5, which also authored 12 of the reports it may adjudicate, and it sees only disagreements (anchoring on the markers' framing is unspecified). The claim that "the per-error rules are written so that style cannot pass for finding" is asserted by the skill's own author and cannot be checked â the rules are sealed from this examination. *Why it matters:* leniency toward skill-styled evidence on HV errors is the exact bias that manufactures a "skill wins" result; self-hostility or self-leniency moves each reader's own numbers, and readers are compared to themselves. *Smallest change:* drop self-marking â Mimo marks Atria's reports and Atria marks Mimo's, with the adjudicator acting as the second marker on those reports (so every report still has two marks and none by its author); have the adjudicator also re-mark a random quarter of agreements to measure style bias, and show per-marker tables next to the agreed one (already promised â keep it).

**8. The decision rule cannot be applied as written.**
*What is wrong:* "A finding on two or more of the four readers ... at the same thinking setting" â Opus has no thinking cells and only S/N, so for ST-vs-NT and SO-vs-NO only three readers exist, and Opus's single contrast is at an uncontrolled setting. "More planted errors found (either kind)" pools HV and GEN although the skill targets HV only. "With false alarms not rising by more than the gain" has no exchange rate (point 5). "A difference of one error in twelve is noise; the results say so for every difference they report" states no threshold and no procedure â everything above one is treated as signal. Per-reader "findings" are vote-counting across incomparable cells. The claim that four cells "separate the skill's effect from thinking's" is not readable at this n (point 9). *Why it matters:* with this much free play, any outcome can be argued after the fact â the round cannot answer the question even if it runs perfectly. *Smallest change:* freeze a numeric rule now: per contrast, per API reader, e.g. "skill effect = mean per-rep difference â¥ 2 of 12 in the same direction in at least 2 of 3 reps"; the decision reads on HV errors alone, GEN reported beside it; "abandon" requires zero such gains *and* no false-alarm rate increase; Opus is reported separately and does not vote.

**9. Three repetitions cannot carry the claims.**
*What is wrong:* Per cell the data are 3 reports Ã 12 binary opportunities, and errors within one report are strongly dependent (a reader in the groove finds more of everything) â the effective n is 3. Differences of two or three errors in twelve are plausible noise; main effects and interaction of the 2Ã2 are unestimable. D3 ("of 6") is one natural error and cannot evidence "finds real errors." *Why it matters:* the plan's own noise allowance (one error) is far too small, so noise will be reported as findings in a table of 4 readers Ã 4 cells Ã 6 columns. *Smallest change:* raise REPS to 5 for the contrasts the decision uses (SO/NO/ST/NT on the three API readers), publish per-repetition counts, and downgrade any rule that fails to survive one more repetition to "signal."

**10. Failed calls silently disappear from the marking and from the denominators.**
*What is wrong:* `mark` builds its list by globbing `*.response.txt`; a job that returned `failed` (5 attempts exhausted, or 400/401/â¦ which is permanent) simply has no file, is never marked, and is never announced. The table's "of 12", "of 6" silently shrink. Failure is condition-correlated (empty content when reasoning eats the budget; length truncation treated as empty and retried into a filter). *Why it matters:* attrition that tracks the treatment biases the comparison and misstates every denominator. *Smallest change:* before `mark`, assert the expected 84 tags are present with non-empty responses; abort otherwise; count and print failures per cell in the table.

**11. Resumability keeps bad bytes forever and stale marks over changed reports.**
*What is wrong:* `call` skips whenever `.response.txt` exists â so a truncated-but-written file (point 4) is permanent and never retried. In `mark`, an id in `MAP.json` stays bound to its tag even if the report is later regenerated with different bytes, and the existing mark output for that id is then `skipped` â marks keyed to text that is no longer there. Stray `.response.txt` files dropped in the readers folder get answer keys and marks. *Why it matters:* the "frozen by SHA-256" discipline of the plan is defeated inside the pipeline; a rerun after a partial failure can silently mix two versions of the data. *Smallest change:* store `response_sha256` in `MAP.json` and delete/rebuild the corresponding marks when bytes change; validate that the globbed tag set equals the expected 84 and reject anything else.

**12. Temperature is unpinned, and the request shape is untested on two of three providers.**
*What is wrong:* "Provider-default temperature" is not a setting: defaults differ across providers and can change mid-run, and if a default is 0 the three "repetitions" are duplicates and the study's n is 1. The pilot was DeepSeek/NO only â it never exercised `stream_options: {include_usage}`, `thinking: enabled`, `reasoning_effort: high`, or the marker body on Atria and Mimo, nor `max_tokens: 48000` against their caps. An unknown/rejected field returns 400, which is in `FINAL`: every call to that provider dies instantly and permanently. *Why it matters:* the run can burn through and produce one provider's worth of data, or three identical copies of each answer. *Smallest change:* pin `temperature` (and `top_p`) in the body; before the counted run make one pilot per provider per thinking setting plus one marker call, and treat 400 as "stop the run and read the error," not "skip."

**13. No integrity checks on the material the plan hashes.**
*What is wrong:* The plan gives md5s for the seeded document, its parent, and a SHA for the sealed list, and says the eight edits matched "each old string once" â but the runner never verifies any of it, never verifies that the clean path is the hashed file 10, and never hashes the skill text (13,648 words "as sent") or asserts it stayed fixed across 72 calls. *Why it matters:* a drifting file or skill directory changes the treatment mid-run with no trace; the "frozen by SHA" claim would then describe the plan, not the run. *Smallest change:* at startup assert both document md5s, record `sha256(skill_text())` in every receipt (or once in a run manifest), and verify the seeded document differs from file 10 in exactly the intended ways (or at least record its diff hash).

**14. Fixed job order ties condition to wall-clock.**
*What is wrong:* `reader_jobs` emits ST first, then NT, SO, NO; the pool drains the list in order, so ST runs in the first wave and NO in the last. Provider load, outages, or a model-version swap during the run then land on specific conditions (the receipt's `model` field would show a swap only if the provider relabels). *Why it matters:* an hour-of-run effect is confounded with the skill and with thinking. *Smallest change:* `random.Random(8080).shuffle(jobs)` per model before running.

**15. The errors, the found-rules and the skill are all the same author's, and only one real error is in play.**
*What is wrong:* The four HV plants are constructed from the skill's own categories ("of the kind the skill is written to find"), planted and rule-written by the skill's author; the only natural error is D3 (n = 1). *Why it matters:* a win shows the skill finds its inventor's textbook examples under rules its inventor wrote; it cannot show it finds errors nobody planted. This is an external-validity ceiling on whatever the round concludes. *Smallest change:* state the scope in the plan's verdict clause ("these eight kinds, on this document"), and add the known natural errors from logs S70âS75 as a small separate column rather than letting D3 stand for "real errors."

**16. Nothing produces the deliverables.**
*What is wrong:* No code parses the markers' JSON, checks it is a single un-fenced object, matches its ids to the key, resolves "in its order," builds the per-marker/agreed tables, or emits "every disagreement is listed." Tag-name parsing (`"_seeded_" in t`) is the only link between files and design cells. *Why it matters:* the analysis step is where flexibility enters after results exist; "the table is given per marker and for agreement" currently has no producer at all. *Smallest change:* write the tabulate-and-validate script before the run (strip code fences, validate ids against the key, fail loudly on parse errors), and parse condition from tags with a strict regex.

**17. The "others" taxonomy double-counts near-misses and games item granularity.**
*What is wrong:* The marker instruction sends "every item that does not count as finding a key error" to GENUINE/MISTAKEN/UNCLEAR â so a report that finds a planted error in words the rule rejects is simultaneously "not found" and "a genuine defect," while a report that merges three complaints into one item collects fewer "false alarms." "How sure" is collected and used nowhere. *Why it matters:* both distortions move the two quantities the decision trades off against each other. *Smallest change:* rule that one key error is judged once (NOT FOUND plus a "partial" flag for the adjudicator, never re-listed as an other), count false alarms per numbered report item, and either use the certainty field (e.g. report "possible"-weighted false alarms) or drop it from the task.

**18. The Opus arm's protocol differs from the API cells and is unauditable.**
*What is wrong:* Opus reads a skill directory with tools while the API trio gets a pasted system prompt; Opus's S agent is told "read the skill's directory first" (extra instruction and work) while N is not given a matched instruction; Opus runs leave no request, receipt, max_tokens, or captured context in `results/`; and the leak check has no pre-stated consequence. The title's "thinking on and off" does not apply to it. *Why it matters:* the arm is not a cell in the same 2Ã2 and cannot vote in the same rule (see 8); unverifiable runs cannot be audited later. *Smallest change:* deliver the task, document and skill to Opus as one assembled message like the others (or report Opus as a separate, non-voting arm), capture its full prompt and output as files, and void any repetition whose contamination check fires.

**19. Small runner defects that will bite.**
(a) Every write uses `open(..., "w")` without `encoding="utf-8"` while the documents and skill carry non-ASCII â under a `LANG=C` venv this raises `UnicodeEncodeError` *outside* the try, killing the whole pool mid-run. (b) `usage` is read from the last chunk and may be absent when `include_usage` is ignored â the "tokens" column then has no source. (c) `key.index("## The error file 10 already carries")` silently couples the runner to one heading's exact wording. (d) Reader reports are pasted into marker prompts with no delimiter â a report containing section headers or imperative text can steer its own marking. *Why it matters:* each is either a mid-run crash or a silently empty column. *Smallest change:* add `encoding="utf-8"` everywhere; fall back to character-count estimates and say so in the table; assert the key headings once at startup; wrap the report in explicit fences with an instruction that text inside is data.
