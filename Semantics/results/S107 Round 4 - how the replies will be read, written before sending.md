## How the replies will be read

1. **Nothing is opened until all four calls end.** No reply, receipt, reasoning file, attempt file, stream file or guard log of this round is opened until every job has ended its last allowed pass (a reply accepted, or failed with no pass left): the run log holds `s107_glm_loop: every pass ended; …` and `loop ended <UTC time>`, and the process in the pid file has exited. The progress lines of the log (start, sent, still running, accepted, not accepted, done) may be watched, by `watch_run.py` or by hand; they hold no reply text. If a call is still running 24 hours after the launch, the orchestrator may stop the runner by its PID and record the calls not ended as not returned; all four have then ended.
2. **What counts as a reply.** A reply counts only when `<tag>.response.txt` is in the returns folder: the helper writes it last, and only for a reply whose last non-blank line carries END OF REPORT. A failed call counts neither for nor against any finding. Connection failures, timeouts, HTTP 429 and 5xx are not answers from the model (lessons S21, S24): the helper tries again; a job failed only on the connection after pass 3 may be sent again only under a new note written before sending. A job failed after pass 3 on answers the model gave (no END OF REPORT) is final, and its job is recorded as **not done by that call**. After a container restart the runner is looked at and relaunched from a shell started after the restart, by the orchestrator. A receipt that shows the key found in the output (`key_found_in_output_and_replaced` above 0), or a sandbox not unchanged, is reported to the orchestrator before anything else is read.
3. **A reply is a set of arguments to rule on, not a result.** Nothing in the maths, the program or the text is kept, changed or dropped on a reader's say-so. Silence is not agreement: a definition no job attacks is not thereby shown to hold, and a claim that held on every model tried holds on nothing beyond them. A model a reply marks "not run" is run by the checker before it is ruled on.
4. **Tabulation first, by Opus.** Once all four calls have ended, **one fresh Opus 5.5 agent**, which built nothing of this round and has read no reply, tabulates the four replies before any ruling (S46: the tabulation stays with Opus; no Sonnet agent takes part): for each finding, its job and id, the items and lines, what fails, the model or computation and whether it was run, the proposal whole, its form (maths, code, or which of the three text changes), and the inventions it rests on. It may run the harness's scripts itself as tools (`tabulation.py blocks`, `quote`) and reads what they print. It flags each proposal that adds prose (not taken, S40), each that would reverse or weaken an owner's answer (not taken, S41 with S47), each that would put the written-in test back into what makes something an explanation (not taken, S44, S45), and each that would have the maths ask for a criticism event (not taken, S47). It writes `results/S107 Round 4 - tabulation of the replies, before any ruling.md`, created at once and filled as it goes (lesson S28), and rules on nothing.

The sizes of the three groups are counted before any checker starts (lesson S36). Each checker, for each finding of its area:
