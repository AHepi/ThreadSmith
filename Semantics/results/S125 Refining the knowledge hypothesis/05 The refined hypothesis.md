## 0. In short

- **Survive, in changed form:** H1 (the knowledge is the programs' arrangement, and its content is the relation that was paid for, not "Avida's random generator"); H2, sharpened (the execution environment's history may carry part of it: untested); H4, local only (nothing in any Avida set-up run so far has been built rather than selected; "cannot" and "never explanatory" do not follow); H5, as an advantage claim (an outside source's structure is used when it drives what is kept), not "only"; H6, revised (construction on selected material is a possible route; one lifetime is a place to look, not the threshold).
- **Dropped as rivals:** H3 (it predicts nothing of its own; what it adds is a choice about the word "knowledge", which goes to the owner); H5's "only" (the record already has learning from an inside source, S120, or else it is true by definition).
- **The refined hypothesis**, in one sentence: *knowledge in an Avida run is a capability-specific arrangement of instructions, held across the program population, that a reliably performed transformation depends on, that the run keeps copying and keeping, whose correspondence is with whatever relation actually drove its retention, and which acts on the execution environment's state through that transformation; in every set-up run so far it is of the adaptive, selected kind.* Section 4 gives its parts, what it predicts, what would count against it, and how it reads under Reading A and B and under the two readings of "Avida itself".
- **Transports:** learning from outside data needs an entry for source-dependent distinctions (as inputs, or as consequences that change selection), working state, an output, a link from that source to what is **retained**, and a candidate class; it does not need constant or live input, a second socket, or a finished model to begin. Stock Avida has all of these but a fair forecast scorer; the entry by events is stock (confirmed by run).
- **Environment:** Avida is closed to outside data by configuration, not by design; most of the "cannot"s in our assessment are configuration choices or bounded extensions; what still needs real building is a fair per-program forecast protocol, per-birth cue episodes, moving objects with occlusion, trace recording for a construction audit, and program-reachable rule data.
- **Next experiment:** reply 03's outward elimination with sham, restoration and blind replay, on S113's saved COMMON TASKS PAY LESS populations: about 1.1 to 1.2 CPU-hours for two saved states, no new C++; routine by the standing rule (under 3 CPU-hours), not run in S125.

## 4. The refined hypothesis

### 4.1 Statement

**Knowledge in an Avida run is a capability-specific arrangement of instructions, held across the program population, such that**
1. **(dependence)** a reliably performed transformation depends on it: removing every instance of it stops the transformation while copying goes on, a matched sham removal does not, and restoring it restores the transformation;
2. **(keeping)** the run keeps it: it is copied with the programs, tolerates the variation of copying, and persists in the lineage (the owner's three properties in S111's measured sense);
3. **(content)** its correspondence is with whatever relation actually drove its retention, not with the origin of the inputs: in every run so far, a task relation named by Avida's checking code, relative to Avida's instruction meanings; about something outside Avida only where that thing's distinctions enter and drive what is retained;
4. **(outward)** through the transformation it depends on, it changes the execution environment's state: resource stores, occupancy, and through them what the execution environment pays for;
5. **(kind)** in every Avida set-up run so far it is of the adaptive, selected kind: no history contains an owned episode that prepares a new binding against a held target (Build, L405).

Two pairs are left open as **problems** (section 4.6): where the arrangement sits (H1' or H2'), and whether a richer set-up can construct (H4-local or H6').

It is a hypothesis about K-CT (clauses 1 and 2: information whose elimination stops a reliable transformation and which keeps itself instantiated), about K-O3 (clause 2, and clause 4 for S76), about K-D's adaptive kind (clause 5), and, conditionally, about K-Sem's representation (section 4.4). It is not a hypothesis about K-P (no within-life learning has been seen) beyond saying where K-P would have to be looked for.

### 4.4 Under S117's open reading

**Reading A** (the checking code is part of the world's rules). Clauses 1, 2, 4 and 5 are causal and read the same. Clause 3's correspondence is **selected** only where the execution environment enacts a survival condition requiring fidelity on the history (D12.1, core L454): a required task (`REQUIRED_TASK`), S118's "copy only after solving", or a reading of graded pay as such a condition, which the text does not give. Where it is selected, the program represents its task relation (D12.5) and, as one block, can meet (E) and so be an explanation of its task in the semantics' narrow sense (S117, B1), never a *created* explanation (no Build). In the graded-pay runs that make up most of the record, selected provenance is **not established** (00, row 15). A forecast of an outside recording selected by a comparator would, under A, be a selected correspondence whose content is about the recording.

**Reading B** (the checking code is an earlier occurrence representing the task). Clause 3's correspondence is **declared**: it holds, faithfully, and represents nothing (L211). The same goes for a forecast of an outside recording as long as a written comparator enacts the survival condition: the comparator represents the survival condition (D12.1's list includes it). Under B, then, no correspondence selected through written checking code represents anything, whatever its data; only a standard not written as checking code (grade 3), or construction, could change that. Clauses 1, 2, 4 and 5 stand unchanged: K-CT and K-O3 knowledge do not need representation.

### 4.5 Under S76's reading of "Avida itself"

**Its rules.** Read as the implemented transition procedure (the C++): no program changes it, and clause 4 makes no claim that one will; in a closed simulation nothing can (R03 L68). Read as the current settings that procedure reads (reaction values, configuration entries): events and drivers change them during a run, programs in the heads set do not. On this reading the knowledge in Avida has **no** effect on Avida itself, and could have one only through an extension that gives programs a route to rule data, an effect that would then run through a route written for it.

**Its state.** Clause 4 says it does, through the resource route that the source implements, and predicts a capability-specific effect for a named task in a resource-coupled set-up. Not yet measured for any capability: this is what the next experiment measures.

### 4.6 The two problems kept open

- **Where (H1' against H2').** Both fit every checked item. They conflict on a valid history swap: with the population and current conditions held equal, H2' predicts a task-specific change in retention or reacquisition, H1' none. The test is reply 03's test 2 (3.15 CPU-hours a panel; it needs an execution environment whose memory is shown active first), or a cheaper first version on resource state (section 7, item 2).
- **Construction (H4-local against H6').** They do not conflict on any set-up run so far; they conflict on a set-up with patterns that vary between lives but hold within one. The test is a within-life learning witness (reply 02), then an audit of an actual episode beside an equal-output relay and an inherited-mapping control (reply 04).

### 4.7 Does it survive the reading? (plan, section 5)

No checked claim counts against it; at least one test that could count against it is well formed and costed (section 7); it says which meanings of knowledge it concerns; it does not depend on any misuse of a semantics term found in the checks (none was found). It **survives the reading**. It has not been run.

## 5. The transports learning from outside data needs to begin, as refined

1. **An entry for source-dependent distinctions**, by either of two routes: as inputs to programs, or as consequences of programs' outputs that change what the execution environment keeps (R01 L107). Stock Avida has the first by events (confirmed) and the second by pay and resource events prepared from data.
2. **Execution with working state**: registers and stacks during a life (present).
3. **An output route** (present: `IO`, output before input).
4. **A link from the source to what is retained** (missing from our list): the scoring must depend on the source, and that score must change which programs are kept (R01 L105). Stock reaction checking does this for task relations; for a forecast of a recording it needs a small gated scorer that takes one committed answer per frame before the reveal.
5. **A candidate class and a variation operator** within which the relation can be reached (present; a restriction, not a transport).

**Not needed to begin:** constant or live input (a recording suffices for a fixed problem; live contact matters only to track change); a second socket (two views can share one); an action loop (only for control tasks); a finished model (L3 is what is assessed). **Needed for more than learning:** fidelity and provenance for representation (D12.5); an object and a simulation layer for prediction and surprise (D12.6, D12.7).

### 7.2 The choice: candidate 1, the outward elimination

**Why this one, per CPU-hour.** It is the only candidate that can make a clause of the refined hypothesis fail with material already in hand and no new C++; both of its outcomes are informative (a capability-specific outward effect, measured for the first time, answers S76 under the state reading; its absence counts against clause 4 and sends the question back to the owner's readings), whereas candidate 2's null would be weak (resource stores relax in about 100 updates at the S113 settings, inflow 100 and outflow 0.01, so a short memory is expected either way) and candidates 3, 5, 8 and 11 wait on a precondition, new code or the owner's word. At about 1.1 to 1.2 CPU-hours it is the cheapest decisive test. **What it does not do**: split H1' from H2', touch outside data, or bear on construction; reply 03 says so itself (R03 L119-121).

**Set-up** (to be written and committed before running, as in S120 and S122): S113's COMMON TASKS PAY LESS, seeds 1 and 2, the saved population at 50,000 updates (piece 49) with its resource levels; q chosen by a rule fixed before any intervention (the task performed by the most programs at that save, ties to the higher value); every sequence performing q found in analyze mode; a cut per sequence that removes q and keeps copying, checked in a common probe environment with pay off; a sham of the same number of removable instructions; the six arms of R03 L104-111 (L0 original, Lq cut, Ls sham, Lr restored; R0 and Rq with L0's resource tape replayed by `SetResource` each update), 5,000 updates each, `PrintResourceData` and `PrintTasksData` every 10 updates; each under `timeout` and `nice -n 19`.
