## 1. The question, and what counts as an instinct in Avida

**The owner's words (S71):** "I don't know yet.  Avida can exhibit a type of autonomy. But can you give it an instinct to solve a problem without specifying exact target goals?"

**As Claude reads it.** Every Avida execution environment tried so far (S111 to S116) pays for a list of tasks written in advance, each an exact target function (NOT, NAND, ..., EQU, the 68 three-input functions), most with their own value. And in Avida, lasting does not require doing any task (S117, break 4). The question: can a program population be given a standing drive to solve problems, where the execution environment does not name which function or which answer is wanted?

**What counts as an instinct in Avida, in this job.** The owner's word is used only in the owner's sense, made exact here:

> An **instinct** is a standing pressure, built into the Avida execution environment or into the Avida programs, (a) that does not name which input-output function or which answer is wanted, (b) under which programs come to perform functions of the numbers handed in (solve problems) that no part of the environment singled out, and (c) that keeps acting: it is not used up once one function is found.

**Three grades of "not naming the target"**, used strictly throughout:

1. **Named exactly**: a list of functions, each with its own pay or requirement (every environment of S111 to S116).
2. **Named one level up**: no single function is singled out, but a class or a rule over functions is written down ("any of these 251 functions", "whichever of them is rare", "at least one of them"). Listing all functions of a class still names the class: "pay for any of the 256 three-input functions" names a list.
3. **Truly unnamed**: nothing in the environment's code computes or names what counts as a solution; the target is set by something outside the checking code that itself changes (other evolving programs; what the world actually does next).

A fact from Avida's design bears on every row below: **whatever Avida pays or requires is decided by C++ code that inspects what a program did** (`main/cEnvironment.cc` `cEnvironment::TestOutput`, from line 1337; `main/cTaskLib.cc`). So in stock Avida a paid or required behaviour is always named at least at grade 2, by the code that checks it. Grade 3 can only come where the checking code compares a program with something it does not itself compute.

## 3. The two pilots, and why

**Chosen:** the two stock mechanisms that most directly answer the owner's question (row 1 with row 4: pay with no function singled out) and S117's break 4 (row 6: lasting requires solving), both with the same 77 tasks, so that "which function" is left open in the same way in both.

**Not chosen for a pilot:** parasites (row 9) and the energy model (row 7) need a different instruction set and ancestor, so the pilots could not start from S113's program; foraging (row 8) poses no problem of computing; deme competition (row 10) needs a different world layout; S115's batches 4 to 9 (including reply 08's growing supply of problems) await the owner's word and are not run here.

**Echo left out.** In a 1,000-update mechanics test with `echo` paid like every other function, 2,818 of 3,599 programs handed a number back unchanged; even unpaid, 261 did. Handing a number back carries information but computes nothing; a requirement or a pay that `echo` meets would be met without solving anything. So, decided before this plan and before any pilot run: `echo` is not listed in either pilot, and the class is the 251 functions of Avida's 77 logic tasks. This also keeps the task list exactly S113's, so the counts compare column by column.

**P1. ANY FUNCTION, RARE PAYS MORE.** All 77 tasks, each paid the same (`value=1.0`, `type=pow`: at most a doubling of the program's processor-time share, once per copy), each from its own resource with S113's COMMON TASKS PAY LESS settings (`inflow=100`, `outflow=0.01`, `frac=0.0025`, `max=1.0`). No function is worth more than another; a function that many programs perform pays less, one that few perform pays more. *How named:* one level up (the class, and "rare pays more"). *Compared with* S113's FIXED LARGE LIST (same 77, each with its own value by difficulty), COMMON TASKS PAY LESS (9 two-input tasks, depleting, valued by difficulty) and NO TASK REWARDS.

**P2. SOLVE SOMETHING TO REPLICATE, NOTHING PAID.** The 77 tasks listed at value 0 (nothing paid). From update 5,000 on, `SetConfig REQUIRE_SINGLE_REACTION 1`: a program completes a copy of itself only if, during that copy, it performed at least one of the 77. Before 5,000 the run is S113's NO TASK REWARDS exactly. Switched on at 5,000, not from the start, because the starting program performs no task and would die out at once (mechanics test, row 6). *How named:* one level up ("at least one of these 251 functions"). *Compared with* S113's NO TASK REWARDS, and with P1.

**Common to both.** Avida stock at commit 47f13dad (`cbuild/bin/avida`, built in S111, unchanged); S111's `avida.cfg`, instruction set and default ancestor (`default-heads.org`, which performs no task); 60 x 60 world; copy error 0.0075. Seeds 1, 2, 3, with Avida seed 1000 k (S113's seed for the first piece of seed k). **20,000 updates** each, one continuous Avida process (no save and reload). Avida prints the task counts and program counts every 250 updates, resources and averages every 1,000, and saves the program population every 5,000. Six runs, at most three at once, each under `nice -n 19` and a 7,200-second timeout. Script: `tools/s118_run_the_two_pilots.py`; raw output in the scratchpad `s118/runs/`, never in git.

**Departures from S113, fixed now.** (1) Continuous runs of 20,000 updates, where S113 ran 50 pieces of 1,000 with a reload between; S114's restart audit found pieces and unbroken runs alike in births and copy times, and a continuous run avoids S113's counting fault after a reload. (2) The comparison is at 5,000, 10,000, 15,000 and 20,000 only. (3) For P2, up to update 1,000 the run should match S113's NO TASK REWARDS first piece of the same seed exactly (same seed, same files); this is checked and reported as a check of the set-up.

## 4. What is measured

- **M1 (both).** Number of the 77 tasks present and common at 5,000, 10,000, 15,000, 20,000, by Avida's own count (`tasks.dat` against `count.dat`), and by the test processor on the saved program populations (every distinct instruction sequence run alone in Avida's analysis mode, as S113 did, with `tools/s113_measure_capabilities_in_the_saved_program_populations.py`'s own function).
- **M2 (both).** Share of programs whose sequence performs at least one task (test processor), and the number of distinct tasks per program (middle and largest).
- **M3 (both).** How hard the common tasks are: the fewest nand steps each needs (S113's ranking file); the largest and the middle.
- **M4 (P2).** Program count and births around update 5,000 (every 250 updates); whether the population dies out; which tasks carry it through.
- **M5 (comparison).** The same counts in S113's raw runs at the same updates (Avida's count from the piece ends; test processor from S113's summary), for FIXED LARGE LIST, COMMON TASKS PAY LESS, FIXED LIST GRADED, GROWING LIST and NO TASK REWARDS.

## 5. What would count for and against

**For an instinct in the sense of section 1, at grade 2 (P1).** By update 20,000, in at least two of three seeds, P1 has at least as many common tasks as S113's FIXED LARGE LIST has at 20,000 in its middle seed by the test processor, and new tasks are still becoming common between 10,000 and 20,000 (the pressure keeps acting). **Against:** in at least two of three seeds, fewer common tasks at 20,000 than S113's COMMON TASKS PAY LESS or FIXED LIST GRADED in their middle seed (an unnamed pay does less than a short named list), or no new common task after 10,000. **Anything between** is reported as mixed.

**For lasting depending on solving (P2, S117 break 4).** In every seed that does not die out, the share of programs performing at least one task goes from its level before 5,000 (expected under 2 in 100, as in S113's NO TASK REWARDS) to at least 90 in 100 by 20,000. **Against:** the population dies out in every seed, or the share stays under 50 in 100 in the seeds that survive. Dying out in some seeds is reported as a result, not hidden.

**For a drive beyond the minimum (P2).** P2 reaches at least as many common tasks at 20,000 as S113's FIXED LIST GRADED at 20,000 in its middle seed. **Against:** P2 settles on one or two of the easiest functions. **Claude's expectation, written now:** P1 will have many common tasks, mostly among the easier three-input functions; P2 will survive in most seeds and settle on one or two easy tasks: a requirement makes a floor, not a drive. These are expectations only.

**How the answer to the owner will be given.** "Yes, at grade 2" if P1 meets its "for" and the table holds (no function singled out, but a class named). "Yes, truly unnamed" cannot be reached by these pilots (section 1): it is said plainly that grade 3 needs either co-evolving programs (row 9) or new C++ (row 5). "No" if P1 meets its "against".

## 6. What is not tested

Grade 3 (truly unnamed targets): prediction of a hidden regularity (C++), open-ended novelty (C++), parasites (stock, not piloted); the energy model; foraging; deme competition; programs judging each other beyond S116's batch 3a; anything longer than 20,000 updates or with more seeds; S115's batches 4 to 9; whether any of this counts as knowledge or explanation in the semantics' sense (S117's open reading stays open). The smallest C++ changes for row 5 and for open-ended novelty are proposed in the results with their cost, not built.

## 7. Cost

Mechanics tests before this plan: two 1,000-update runs (40 and 24 CPU-seconds), one 600-update switch test (under a second) and one 600-update switch probe (a few seconds), one 300-update requirement test with a NOT program (a few seconds); all in the scratchpad `s118/test*`. The six runs: S113 needed about 90 to 120 CPU-seconds per 1,000 updates late in a run, so about 0.5 to 0.7 CPU-hours per run, 3 to 4 CPU-hours in all, about 1.5 hours of wall time at three at once; the test-processor counts a few CPU-minutes. If the runs approach the job's budget of about 4 CPU-hours, the remaining runs are stopped (by exact process number) and recorded as proposed with their cost.
